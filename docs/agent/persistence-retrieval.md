# Persistence and retrieval

`src/memory-core/` is the sole durable core. `contracts.ts` defines public application records, `sqlite/` owns the current schema/ledger/FTS transaction, `service.ts` is the shared seam, and `retrieval/projections.ts` records disposable optional-lane lineage.

Session-attributed writes have two layers. Immutable `evidence` keeps the captured payload; `session_events` assigns database-ordered per-session sequence plus closed actor, authority, retention, and privacy classifications in the same transaction. Duplicate save receipts are bound to the original project and session identity: replay in the same session returns the first event, while reuse under another session fails closed without consuming sequence. Project-only explicit evidence remains valid without fabricated session ordering; generic MCP sessionless saves instead receive the server's unverified per-connection `mcp` session (see [MCP launch attribution](native-lifecycle.md#mcp-launch-attribution)).

Session summaries are versioned derived projections, not evidence and not promoted memory. A checkpoint or final summary submission records immutable canonical submission evidence, generator metadata, inclusive source coverage, atomic claims, and per-claim support IDs. Every support must resolve to the same project and root session inside the declared range. The prior current version becomes superseded but remains inspectable; the current projection can be rebuilt deterministically from its submission evidence. The core validates submitted structures or deterministically derives harness summaries without model or network calls. With no submitted summary, `checkpoint_pre_compact` and `finalize` derive from citable session evidence; no citable evidence means no summary.

Derivation uses generator `thoth-mem.session-evidence.v2`. Objectives come from the first and latest distinct substantive root prompts (at least 40 Unicode code points after whitespace collapse), falling back to only the first prompt when none qualifies. Decision, convention, architecture, and preference memories map to decisions; discovery and project-structure memories to completed work; failures to completed claims with `failed` outcome; open handoffs to next actions; and closed handoffs to completed work. Each memory claim uses its title plus the primary labeled line: `Result:` for direct memories, `First pending action:` for open handoffs, the closure's `Result:` for closed handoffs, or otherwise the first line. Identical kind/content claims collapse with merged supports up to the support limit, preserving failed outcomes.

Derivation also reuses the newest parsed host compaction claims. `guide_post_compact` content is sanitized checkpoint evidence: recognized Markdown headings map goal/request/intent to objective, done/completed to completed, in progress/pending to pending, blocked to blocker, decisions to decision, next steps to next action, and modified files to changed surface. Only the first objective section contributes an objective; paths from all modified-files sections and `<modified-files>` blocks merge into one deduplicated changed-surface claim in first-seen order. Unrecognized text remains evidence only, never a memory or observation.

The activity watermark is the latest non-`session_summary` evidence sequence. Derivation is idempotent per session, summary kind, and watermark; persisting a summary cannot retrigger it, and checkpoint/finalize retries return their original receipt. Same-watermark summaries, including existing v1 summaries, are reused without regeneration. Lazy derivation touches only the selected previous session when its latest summary does not cover that watermark, producing a final summary for an ended session and a checkpoint otherwise. Derived objective, memory, and compaction claims are bounded to 300 Unicode code points. Same-session support rules and submission limits remain unchanged: 32 claims, 2,000 code points per claim, 16 supports per claim, and 20,000 UTF-16 units overall.

Evidence is immutable source material; promoted memory is a selective typed interpretation that must link supporting evidence. A lifecycle checkpoint or summary does not promote a `handoff`. Promote only information that materially changes how a future coding agent acts. Preserve `failed`, `mixed`, `succeeded`, or `unknown` outcomes, and reuse a stable topic key when a correction appends a replacement, closes the prior validity interval, and keeps superseded history. Confirmed saves and FTS visibility commit together. Startup rejects a legacy schema without mutation; only the explicit `import-legacy plan`/`apply` workflow may reconcile one into a distinct current target. Planning is zero-write and hash-binds the source, target, project mappings, row dispositions, and policy. Apply revalidates those inputs, works on a candidate copied from a verified backup, and publishes only a closed, verified SQLite file; the legacy source is never mutated.

Legacy `sessions`, `user_prompts`, `observations`, and optional `observation_versions` are authoritative inputs. Legacy FTS, vector/graph tables and shadows, access or maintenance state, telemetry, jobs, and other projections are derived or unsupported inventory only and are never selected as source rows. Exact identity, exact path alias, or an explicit reviewed mapping may join a legacy project to an existing project; unmatched non-placeholder identities receive deterministic `legacy:` isolation, while placeholders, ambiguity, row/session conflicts, deleted material, unsupported kinds, and unsafe or malformed private content are explicitly skipped or quarantined. Taxonomy policy `legacy-taxonomy-bugfix-v1` maps `bugfix` histories to `discovery` memories with `succeeded` outcome and preserves `legacy_kind: bugfix` in their immutable evidence metadata; `manual` and `pattern` remain auditable quarantine dispositions. Supported prompts remain evidence-only. Supported summaries, observation revisions, and heads preserve their source time and temporal lineage as legacy evidence and historical memory, with exact-content provenance linking instead of duplicate recall records. Import never invents current observation candidates, reviews, promotions, structured session summaries, or session events, and never demotes an existing current topic winner.

Observations are the durable review queue between source evidence and promoted memory. A candidate is one bounded atomic claim with an exact proposed memory, original support IDs, closed kind/scope/generator values, optional advisory facets, and an immutable canonical submission. Session scope requires verified session identity plus in-range same-session supports; project scope permits same-project supports without inventing session coverage. Candidates, facets, reviews, promotions, and idempotency receipts are rebuildable projections over canonical observation evidence. They never enter `memories` or `memory_fts` merely because they were submitted or reviewed.

A non-import verified root session appends one terminal accepted or rejected review. `root_user_confirmed` requires an attributable same-session root prompt; `observable_validation` requires a same-session typed validation receipt and is limited to observable claim kinds; `independent_review` requires a matching harness attestation from a different non-import session and has the same kind restriction. Promotion remains a separate explicit root operation, accepts no replacement prose, and atomically materializes the accepted proposed memory with original support, candidate, review, and promotion lineage. Rejected or unreviewed candidates cannot promote. Corrections append a non-branching successor candidate; topic-key promotion supersedes the prior current memory while retaining history.

Recall is lexical-first, sanitizes FTS syntax, uses deterministic ties, prefers current guidance, and reports optional lane state without depending on it. The runtime default `strict-selected-any-cap5-stable-v1` keeps the bounded strict/relaxed FTS eligibility stages but replaces corpus-dependent BM25 ordering with a fixed score over only the query, title, content, and topic key. Exact ID/topic matches remain first. Lexical results are filled oldest cohort first: native and exact-linked memories are cohort zero, then imported cohorts use their immutable numeric sequence. A later import therefore cannot reorder a complete older Top-K; when older cohorts fill the limit, broad textual queries may intentionally starve imported rows. Distinctive imported text is guaranteed only when older cohorts leave capacity, while exact imported ID/topic access remains unconditional. The archived strategies remain selectable only for frozen comparisons.

Project timeline exploration is a separate structured read, not a lexical lane. `mem_project action=timeline` selects promoted memories only from the exact verified project, includes current, superseded, retracted, and historical states, and orders semantic time by SQLite `julianday(valid_from) DESC, id ASC`. Optional `since` and `until` instants are inclusive and normalized to UTC; a versioned opaque cursor is bound to the resolved project and those normalized bounds. Pages use a 1–100 item limit, a 1,024–20,000 effective aggregate character budget, Unicode-safe compact title/topic/snippet fields, and truthful `hasMore`/`nextCursor` metadata. The cursor is a live keyset continuation rather than snapshot isolation, so a fresh traversal is required to include concurrent backdated inserts. Timeline results expose no evidence IDs, raw support, summary, observation, or session-event data; expand only selected memory IDs through `mem_get`. The read uses the authoritative `memories` table directly and adds no schema revision, projection, FTS behavior, or automatic context input.

The shared selector has explicit and recovery modes: `service.context(input, 'recovery')` selects the newest open handoff, then the previous session's newest current summary, then other project memories. Previous means the most recent other root session of this project by non-summary activity, from any harness. Automatic native recovery, per-prompt refresh, and `guide_post_compact` all use this mode, never the current session's own summary. Explicit `mem_context` and `mem_project action=briefing` with a verified session pair retain own-summary-first selection; summary precedence uses source coverage, final-before-checkpoint ties, and deterministic version ordering. Without a pair, project context uses the most recent session as predecessor; generic MCP injects its connection pair and uses recovery mode. Remaining memory order is unchanged: decisions/conventions, failed or mixed lessons, other failures, project structure, remaining kinds, then older unclosed handoffs. Degraded or premature post-compaction events still fail closed. Selection remains deterministic, bounded by the unchanged aggregate and host caps, and never reads raw support evidence into recovery.

Agent-authored handoffs (`save` and observation proposals) require a `topic_key`; a later memory under the same key, such as a succeeded closure decision, supersedes and thereby closes the handoff. Such a non-handoff closure record stays current and retrievable but is excluded from continuation selection, so closures never displace useful memories. Imported legacy summaries are exempt.

Compact recall, context, briefing, and timeline expose stable memory or summary IDs only. Use `mem_get`, `mem_project action=summaries`, `mem_project action=history`, or the explicit `mem_project action=observations` queue after selecting a record to obtain structured claims, support IDs, evidence IDs, and temporal lineage. Observation queue output is bounded, withholds raw support payloads, partitions current correction leaves from historical predecessors, and orders state/time/ID deterministically. Host-visible recovery and Skill guidance label historical content as untrusted data, withhold raw support payloads, and preserve selective expansion. No graph, vector, entity, reranker, or consolidation projection participates in the baseline. An optional module may be added only after equal Top-K and final-context budgets show a reproducible quality gain without violating latency, memory, provenance, privacy, or host-cap gates.

`mem_project action=summaries` lists records newest first within `budget_chars`; records that fit are unchanged. An oversized record retains all metadata and as many leading claims as fit, clipping the last included claim by code point when needed, with item `truncated: true`. Listing then stops with `payload_truncated`; a budget that holds a record's metadata never hides it behind an empty list. Use `mem_get` for the full record.

The current schema is revision 11. The revision-10→11 step creates or verifies `memory.sqlite.pre-v11.bak`, rechecks the source under an immediate write-excluding transaction, and deletes only unreferenced non-import sessions plus their lifecycle receipts with null `evidence_id` and `summary_id`. Evidence, session events, summaries, observations, reviewer-session and legacy-import references, and lifecycle receipts citing evidence or a summary all protect a session. Import sessions and all referenced rows remain unchanged; reopening revision 11 is a no-op. Revision-9 databases first pass through the revision-10 Pi harness migration described in [native lifecycle](native-lifecycle.md#revision-10-migration).

Revision 9 creates a verified `.pre-v9.bak` for revision-8 files and adds immutable `legacy_import_cohorts`: exactly one positive, unique, gap-free sequence per committed import. Existing imports are backfilled deterministically by `(created_at,id)`; new imports allocate transactional `max+1`, so equal or backward timestamps cannot change precedence and replay allocates nothing. A memory's lexical cohort is the minimum sequence among receipts whose disposition is `imported`; later `linked` receipts never move it. Revision 8 retains its verified `.pre-v8.bak` and closed import-audit boundary—`legacy_imports`, `legacy_project_mappings`, and `legacy_import_rows`—which binds plans, mappings, dispositions, lineage, and replay receipts without becoming an alternative memory source. Revision 7 adds exact globally unique path aliases after a verified `.pre-v7.bak`; the first verified Git lifecycle may transactionally re-key one deterministic path project to its local UUID, while other matching rows and all content remain untouched. Alias collisions fail closed. Revision 6 remains the observation-projection step: revision-5 databases first create their verified `.pre-v6.bak`, add empty observation projections, preserve prior evidence/memory/summary rows and exact memory FTS state, and never reinterpret historical material as observations. Rebuild parses immutable canonical observation/review/promotion evidence in ledger order, reconciles exact promoted-memory lineage, and fails transactionally on malformed or impossible state. Beyond the empty-session cleanup, physical retention execution, deletion/revocation cascades, and broader capability policy remain later governance work; logical rejection and correction history do not claim physical deletion. Repository verification does not authorize a rehearsal against real databases or a production cutover; both remain separate stateful operations requiring explicit scope.

Start with `tests/memory-core/`; schema changes require focused tests, `pnpm run build`, and `pnpm test`.
