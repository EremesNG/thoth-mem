# Persistence and retrieval

`src/memory-core/` is the sole durable core. `contracts.ts` defines public application records, `sqlite/` owns the current schema/ledger/FTS transaction, `service.ts` is the shared seam, and `retrieval/projections.ts` records disposable optional-lane lineage.

Verified future session writes have two attributable layers. Immutable `evidence` keeps the captured payload; `session_events` assigns database-ordered per-session sequence plus closed actor, authority, retention, and privacy classifications in the same transaction. Duplicate save receipts are bound to the original project and session identity: replay in the same session returns the first event, while reuse under another session fails closed without consuming sequence. Project-only explicit evidence remains valid without fabricated session ordering.

Session summaries are versioned derived projections, not evidence and not promoted memory. A checkpoint or final summary submission records immutable canonical submission evidence, generator metadata, inclusive source coverage, atomic claims, and per-claim support IDs. Every support must resolve to the same project and root session inside the declared range. The prior current version becomes superseded but remains inspectable; the current projection can be rebuilt deterministically from its submission evidence. The core validates this externally supplied structure and never calls a model or network service to create it.

Evidence is immutable source material; promoted memory is a selective typed interpretation that must link supporting evidence. A lifecycle checkpoint or summary does not promote a `handoff`. Promote only information that materially changes how a future coding agent acts. Preserve `failed`, `mixed`, `succeeded`, or `unknown` outcomes, and reuse a stable topic key when a correction appends a replacement, closes the prior validity interval, and keeps superseded history. Confirmed saves and FTS visibility commit together. Startup rejects a legacy schema without mutation; only `import-legacy` may read it, read-only, into a distinct target.

Recall is lexical-first, sanitizes FTS syntax, uses deterministic ties, prefers current guidance, and reports optional lane state without depending on it. The shared continuation selector powers `mem_context`, `mem_project action=briefing`, and native recovery. With an exact verified root session it selects the newest eligible current session summary first, using source coverage, final-before-checkpoint tie-breaking, and deterministic version ordering. Remaining budget may contain current promoted memories. Without an eligible summary it falls back to the existing handoff-first policy, then decisions/conventions, failed or mixed lessons, project structure, and remaining current promoted memories. Project-only context never guesses a session summary. Selection is project-scoped, deterministic, bounded by one aggregate budget, and never reads raw support evidence into recovery.

Compact recall, context, and briefing expose stable memory or summary IDs only. Use `mem_get`, `mem_project action=summaries`, or `mem_project action=history` after selecting a record to obtain structured claims, support IDs, evidence IDs, and temporal lineage. Host-visible recovery labels all historical content as untrusted data, withholds raw support payloads, and reports summary and memory selections separately. No graph, vector, entity, reranker, or consolidation projection participates in the baseline. An optional module may be added only after equal Top-K and final-context budgets show a reproducible quality gain without violating latency, memory, provenance, privacy, or host-cap gates.

Revision-3 databases upgrade forward with a verified file backup before the revision-4 transaction. Existing evidence, memories, FTS state, and lifecycle receipts remain authoritative; migration never invents historical event order, trust metadata, summaries, or observations. Durable observations, review/promotion states, retention execution, revocation cascades, and capability policy remain later staged changes and must not be inferred from the summary tables.

Start with `tests/memory-core/`; schema changes require focused tests, `pnpm run build`, and `pnpm test`.
