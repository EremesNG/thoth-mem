# Persistence and retrieval

`src/memory-core/` is the sole durable core. `contracts.ts` defines public application records, `sqlite/` owns the current schema/ledger/FTS transaction, `service.ts` is the shared seam, and `retrieval/projections.ts` records disposable optional-lane lineage.

Verified future session writes have two attributable layers. Immutable `evidence` keeps the captured payload; `session_events` assigns database-ordered per-session sequence plus closed actor, authority, retention, and privacy classifications in the same transaction. Duplicate save receipts are bound to the original project and session identity: replay in the same session returns the first event, while reuse under another session fails closed without consuming sequence. Project-only explicit evidence remains valid without fabricated session ordering.

Session summaries are versioned derived projections, not evidence and not promoted memory. A checkpoint or final summary submission records immutable canonical submission evidence, generator metadata, inclusive source coverage, atomic claims, and per-claim support IDs. Every support must resolve to the same project and root session inside the declared range. The prior current version becomes superseded but remains inspectable; the current projection can be rebuilt deterministically from its submission evidence. The core validates this externally supplied structure and never calls a model or network service to create it.

Evidence is immutable source material; promoted memory is a selective typed interpretation that must link supporting evidence. A lifecycle checkpoint or summary does not promote a `handoff`. Promote only information that materially changes how a future coding agent acts. Preserve `failed`, `mixed`, `succeeded`, or `unknown` outcomes, and reuse a stable topic key when a correction appends a replacement, closes the prior validity interval, and keeps superseded history. Confirmed saves and FTS visibility commit together. Startup rejects a legacy schema without mutation; only `import-legacy` may read it, read-only, into a distinct target.

Observations are the durable review queue between source evidence and promoted memory. A candidate is one bounded atomic claim with an exact proposed memory, original support IDs, closed kind/scope/generator values, optional advisory facets, and an immutable canonical submission. Session scope requires verified session identity plus in-range same-session supports; project scope permits same-project supports without inventing session coverage. Candidates, facets, reviews, promotions, and idempotency receipts are rebuildable projections over canonical observation evidence. They never enter `memories` or `memory_fts` merely because they were submitted or reviewed.

A non-import verified root session appends one terminal accepted or rejected review. `root_user_confirmed` requires an attributable same-session root prompt; `observable_validation` requires a same-session typed validation receipt and is limited to observable claim kinds; `independent_review` requires a matching harness attestation from a different non-import session and has the same kind restriction. Promotion remains a separate explicit root operation, accepts no replacement prose, and atomically materializes the accepted proposed memory with original support, candidate, review, and promotion lineage. Rejected or unreviewed candidates cannot promote. Corrections append a non-branching successor candidate; topic-key promotion supersedes the prior current memory while retaining history.

Recall is lexical-first, sanitizes FTS syntax, uses deterministic ties, prefers current guidance, and reports optional lane state without depending on it. The shared continuation selector powers `mem_context`, `mem_project action=briefing`, and native recovery. With an exact verified root session it selects the newest eligible current session summary first, using source coverage, final-before-checkpoint tie-breaking, and deterministic version ordering. Remaining budget may contain current promoted memories. Without an eligible summary it falls back to the existing handoff-first policy, then decisions/conventions, failed or mixed lessons, project structure, and remaining current promoted memories. Project-only context never guesses a session summary. Selection is project-scoped, deterministic, bounded by one aggregate budget, and never reads raw support evidence into recovery.

Compact recall, context, and briefing expose stable memory or summary IDs only. Use `mem_get`, `mem_project action=summaries`, `mem_project action=history`, or the explicit `mem_project action=observations` queue after selecting a record to obtain structured claims, support IDs, evidence IDs, and temporal lineage. Observation queue output is bounded, withholds raw support payloads, partitions current correction leaves from historical predecessors, and orders state/time/ID deterministically. Host-visible recovery labels all historical content as untrusted data, withholds raw support payloads, and reports summary and memory selections separately. No graph, vector, entity, reranker, or consolidation projection participates in the baseline. An optional module may be added only after equal Top-K and final-context budgets show a reproducible quality gain without violating latency, memory, provenance, privacy, or host-cap gates.

The current schema is revision 6. Revision-5 databases upgrade forward only after a verified `.pre-v6.bak` file backup; migration creates empty observation projections, preserves prior evidence/memory/summary rows and exact memory FTS state, and never backfills or reinterprets historical material as observations. Rebuild parses immutable canonical observation/review/promotion evidence in ledger order, reconciles exact promoted-memory lineage, and fails transactionally on malformed or impossible state. Physical retention execution, deletion/revocation cascades, and broader capability policy remain later governance work; logical rejection and correction history do not claim physical deletion.

Start with `tests/memory-core/`; schema changes require focused tests, `pnpm run build`, and `pnpm test`.
