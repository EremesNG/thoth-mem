# Requirements checklist: Establish Observation Promotion Pipeline

**Activation reason**: High authority and failure risk. This change introduces durable derived claims, terminal root review, promotion into normal recall, a forward SQLite migration, poisoning boundaries, and an outcome gate whose failure must not alter current defaults.

## Initial validation

- [x] CHK001 [Completeness] Do US1-US5 cover every actor and flow: candidate generator, project/session-scoped submitter, root reviewer, promoter, maintainer/operator, normal recall consumer, migration/rebuild operator, and benchmark maintainer? Evidence: each actor has an independent test and acceptance scenarios in `spec.md`; automatic/degraded/delegated callers are explicit failure actors.
- [x] CHK002 [Clarity] Is the boundary between deliberate direct promotion and candidate promotion unambiguous? Evidence: intent, FR-011, assumptions, plan flow, and contract union retain the current direct branch only for already-authorized information and reserve candidates for claims requiring review.
- [x] CHK003 [Clarity] Can candidate, evidence, summary, review, promotion, and memory be interpreted as distinct authority layers? Evidence: FR-001-FR-003, `data-model.md#Authority layers`, and out-of-scope rules state source, derived, terminal-review, and recall authority separately.
- [x] CHK004 [Consistency] Do stories, FRs, SCs, assumptions, plan, data model, and contract agree that observations never enter normal recall before promotion? Evidence: US3, FR-002/012/017, SC-003, the FTS model, unchanged workflows, and the outcome control all require the same behavior.
- [x] CHK005 [Consistency] Do correction and contradiction rules avoid conflicting mutable-state and governance promises? Evidence: US2 scenario 5 and edge cases require a new predecessor-linked candidate plus existing memory supersession/retraction; full physical cascade remains explicitly out of scope.
- [x] CHK006 [Measurability] Does every buildable SC state observable counts or invariants? Evidence: SC-001 requires zero-side-effect invalid cases; SC-002 requires one terminal verdict, zero invalid promotions, and exactly one memory; SC-003 requires exact six tools and zero leakage/promotion; SC-004 requires zero backfill and every prior row/FTS entry preserved.
- [x] CHK007 [Measurability] Does SC-005 predeclare an equal-budget outcome rather than asserting benefit? Evidence: identical final corpora/order/caps/ratio, zero harmful promotions/calls, p95 and SQLite at most 2x control, attributable resource reporting, and no gate relaxation are explicit.
- [x] CHK008 [Coverage] Is every requirement mapped to a story, success criterion, technical decision, path, and verification seam? Evidence: FR-001, FR-002, FR-003, FR-004, FR-005, FR-006, FR-007, FR-008, FR-009, FR-010, FR-011, FR-012, FR-013, FR-014, FR-015, FR-016, FR-017, and FR-018 each appear in a US Covers list and the plan requirement table; SC-001, SC-002, SC-003, SC-004, and SC-005 each have an independent fixture seam.
- [x] CHK009 [Coverage] Are failure modes complete across input, identity, scope, support, review, promotion, replay, migration, rebuild, retrieval, and report validation? Evidence: edge cases and story scenarios cover malformed/unknown/private/oversized input, partial/degraded identity, cross-scope/range, self-support, invalid basis, duplicate verdict, rejected promotion, content drift, rollback, tampering, contamination, and incomplete evidence.

## Domain lenses

- [x] CHK010 [Security] Can untrusted tool/model/retrieved text grant authority or trigger promotion? Evidence: generator confidence is non-authoritative; acceptance requires verified root identity, canonical basis, appropriate supports, and explicit promotion; automatic capture and similarity transitions are forbidden.
- [x] CHK011 [Security] Is persistent poisoning evaluated at both write and later retrieval boundaries? Evidence: US5 includes poisoned/unsupported cases, SC-002 gates promotion, SC-003 gates recall contamination, and FR-018 requires harmful/unsupported-promotion accounting.
- [x] CHK012 [Privacy] Are private blocks/raw supports/advisory facets bounded and prevented from leaking into model-visible outputs? Evidence: privacy filtering precedes canonical hashing, queue/get omit raw support content, facets confer no authority, and FR-015 preserves native allowlists.
- [x] CHK013 [Migration] Does the requirement set preserve user data and avoid invented history? Evidence: US4/FR-006/SC-004 require verified backup, forward transaction, zero backfill, prior row/FTS preservation, deterministic rebuild, rollback, and no down-migration.
- [x] CHK014 [Performance] Are extra integrity costs isolated from normal recall and objectively bounded? Evidence: no observation FTS trigger/read occurs in normal recall; SC-005 compares identical final corpora and binds normal-recall p95/SQLite bytes to at most 2x control while separately reporting write path costs.
- [x] CHK015 [Domain authority] Is policy-basis behavior sufficiently closed for each observation kind? Evidence: edge cases, contract, and `data-model.md#Terminal reviews` define an exact kind/basis matrix plus evidence kind, project/session, actor/authority, structured payload, observation, verdict/result, and time checks for both acceptance and rejection.
- [x] CHK016 [Domain lineage] Can every promoted memory be traced without treating its submission as self-support? Evidence: candidates require original support evidence, self-support is forbidden, review has separate supports, and FR-003/SC-002 require memory links through promotion/review to original evidence.
- [x] CHK017 [Temporal semantics] Are public `current|history` and queue order executable? Evidence: candidate lineage is acyclic/non-branching; current leaves and historical non-leaves are disjoint; omission defaults current; filters precede caps; state, creation time, and ID form a total order.
- [x] CHK018 [Outcome gate] Can a failed outcome be mistaken for closeout readiness? Evidence: SC-005 remains fail-closed and T033 stays unchecked/change active for any failure or residual risk; both SC-005 and final Oracle must PASS before closeout.
- [x] CHK019 [Public executability] Can every accepted review basis be produced without internal SQL seeding? Evidence: the strict direct-save evidence union exposes only exact validation and independent-attestation metadata variants, requires an existing same-project candidate/session/event identity, forbids simultaneous memory/arbitrary metadata, and T001/T003/T008/T009/T012/T013 cover contracts through MCP.
