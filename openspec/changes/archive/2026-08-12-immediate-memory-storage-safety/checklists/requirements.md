# Requirements checklist: Immediate Memory Storage Safety

**Activation reason**: The change alters the success/failure boundary of durable writes and introduces explicit irreversible deletion of a historically large trace table. Migration, atomicity, scope, concurrency, and preservation requirements therefore have high contract and failure risk.

## Initial validation

- [x] CHK001 [Completeness] Do the requirements identify every actor, flow, failure, and constraint? Yes — operators own preview/apply administration in US2/US4; local writers and sync exporters are covered by US1; owner/non-owner bridges are covered by US3; FR-001 through FR-015 cover startup, write, repair, tracing, retention, config, CLI/HTTP, and live-data exclusion; edge cases cover failures and concurrency.
- [x] CHK002 [Clarity] Does each requirement have one observable interpretation? Yes — the data model defines stable identity, compatible newest-event coverage, exact scopes, deterministic order, strict cutoffs, canonical timestamps, 10,000/50,000 batch limits, bounded samples, transaction snapshot timing, and exact CLI/HTTP names.
- [x] CHK003 [Consistency] Do stories, requirements, criteria, assumptions, dependencies, and non-goals agree? Yes — all four stories are P1 but independently testable; fail-closed writes align with repair and sync convergence; preview-first administration aligns with the no-live-mutation boundary; physical compaction, schedulers, dashboard controls, and new MCP tools remain consistently excluded.
- [x] CHK004 [Measurability] Is objective evidence defined for every requirement and success criterion? Yes — SC-001, SC-002, SC-003, SC-005, SC-007, SC-008, and SC-009 are mapped to deterministic automated seams; outcome SC-004, SC-006, and SC-010 name later authorized production observations and are not misrepresented as repository tests.
- [x] CHK005 [Coverage] Is every story, FR, SC, actor, and failure mode mapped? Yes — US1 maps FR-001, FR-002, FR-003, SC-001, and SC-002; US2 maps FR-004, FR-005, FR-006, FR-007, FR-015, SC-003, and SC-004; US3 maps FR-008, FR-014, SC-005, and SC-006; US4 maps FR-009, FR-010, FR-011, FR-012, FR-013, SC-007, SC-008, SC-009, and SC-010. Invalid scope, journal failure, migration repetition, missing identity, state mismatch, concurrency, malformed time, boundary time, bounded continuation, and apply rollback each have explicit expected behavior.

## Domain lenses

- [x] CHK006 [Data integrity] Do requirements prevent false success and unintended primary-memory mutation? Yes — FR-002/FR-003 require one commit boundary; FR-005 preserves primary state; FR-010 limits deletion to operation traces; SC-002/SC-003/SC-007 assert rollback and unrelated-table invariants.
- [x] CHK007 [Migration] Are legacy, repeated, partial, and read-only startup behaviors explicit? Yes — FR-001 and SC-001 require additive idempotent convergence with row/index preservation, the edge cases preserve null legacy project values, and read-only mode forbids migration.
- [x] CHK008 [Destructive operations] Is irreversible trace deletion conservatively authorized and bounded? Yes — preview is the default on CLI/HTTP, apply is explicit, exact scope is mandatory, status-aware cutoffs preserve recent/errors, one run is capped, malformed/boundary rows are skipped, no VACUUM occurs, and live apply needs separate authorization.
- [x] CHK009 [Concurrency and idempotence] Can repair/prune races or retries create unreported effects? No — apply requires the preview fingerprint; retention also requires its exact effective instant; immediate transactions recompute scope/policy/candidate fingerprints before writes; mismatches return stale-preview failure with zero effects; matching replay/convergence and fresh-empty preview behavior are measurable.
- [x] CHK010 [Performance] Are high-volume operations bounded without adding more dominant indexes? Yes — repair selects at most 10,000, trace deletion at most 50,000, returned identifiers are capped at 50, deletes are parameter-safe chunks inside one transaction, and the existing started-at index is reused.
- [x] CHK011 [Privacy and public contract] Do new outputs avoid raw memory/trace payload disclosure and preserve stable surfaces? Yes — results contain counts, identities, and bounded trace IDs only; retained trace sanitization remains FR-014; commands/routes are additive and mirrored; MCP remains exactly six tools under SC-008.

## Revalidation

- [x] CHK012 [Clarity/Coverage] Were affected requirements revalidated after defining compatible-event repair and the inbound-sync exception? Yes — FR-002, the repair edge case, assumptions, and out-of-scope text now distinguish local writes from inbound replication and observable event gaps from unreconstructable payload history; plan and tasks already implement and test that same boundary.
- [x] CHK013 [Correctness/Revalidation] Were all Oracle blockers repaired across requirements, design, contracts, and tests? Yes — FR-003 and SC-002 now require origin-aware zero-journal inbound application and non-empty local identities; FR-004 through FR-007 and FR-010/FR-012/FR-013 bind apply to preview outputs with zero-write conflict semantics; FR-005 and SC-003 require idempotent observation upsert/resurrection proven by export/import round trip.
- [x] CHK014 [Correctness/Revalidation] Were the fresh pre-implementation Oracle contradictions removed? Yes — project migration now preflights every affected observation/prompt identity and emits state-compatible update/delete events atomically; repair results define `skipped` as already-covered rows, keep ineligible identities separate, and enforce `scanned = candidates + skipped + ineligible_identity` across the model, public contract, and tests.
